# 总延迟实测校准

> 适用：协议 v3（RTP/Opus，固定 10 ms 帧）。
> 目标：把"总延迟估算"的绝对值钉准一次，并确认 `audible_ts` 到底含不含声卡 DMA 缓冲。

---

## 1. 先弄清三个量的关系

| 量 | 含义 | 获取方式 |
| --- | --- | --- |
| `water_ms` | 抖动缓冲 + 解码环 + 声卡缓冲（**单一口径**） | 接收端自算：`jb.water_ms() + ring_ms + device_latency_ms` |
| `device_latency_ms` | 数据填进声卡缓冲到真正发声的时间 | cpal `timestamp().playback − .callback` 实测 |
| `total_latency` | 正在播放的那一帧"到达本机"到"出声"的时长 | `now − arrival(audible_ts) + device_latency_ms` |

必须明确：**`played_frames` 不含 DMA 缓冲**。cpal 输出回调每填一次缓冲就把
`played_frames` 前移，而这段数据还要经过 WASAPI 引擎缓冲 + DMA 才出声。
代码里把 `device_latency_frames()` 并进 `pipe_ms`，`audible_ts` 用
`jb.next_ts() − (ring_frames + device_latency_frames) × current_ratio()` 换算，
因此它对应**可听位置**。`device_latency_ms` 就是从回调时间戳实测出来的那个差值。

`total_latency` **不含**发送端采集→发包与单程网络时延——没有跨设备时钟就测不出来。
所以它是"这段音频到了本机之后又等了多久"，是个下界。

## 2. 打印基线（不需要任何外部设备）

启动后每 10 s 会有一行日志：

```
[Latency] 总延迟≈170ms（水位 150ms = 抖动 96 + 解码 44，目标 150）声卡 10ms 比率 -0.005%（反馈 -46ppm / 前馈 +4ppm，σ 13.0ppm，24 桶，阶跃裁剪 0 帧）
```

（示例数值，实际以本机日志为准。）

判读：

| 现象 | 结论 |
| --- | --- |
| 水位在 130–170 ms 之间小幅波动，标准差 <25 ms | 正常。PI 把水位钉在目标上（无静差） |
| 比率长期顶在 ±0.500% | 两端时钟差超过 5000 ppm，或水位在被外部因素推走——检查是否有进程在改设备采样率 |
| 前馈长期贴 ±20000ppm | 说明不是钟差而是阶跃（改采样率/节拍重置），应走 resync |
| `σ` 长期很大（>200ppm）或桶数不涨 | 到达时刻观测不足（丢包严重/包间隔异常），前馈在裸奔，只剩 PI |
| 反馈量长期顶满而前馈≈0 | 有持续偏差没被前馈吸收（前馈窗口没攒够，或 ts 基准刚被 resync 重置） |
| `声卡 0ms` | cpal 该后端未提供 `playback` 时间戳（换 WASAPI 独占/共享后再看） |

## 3. 实测校准

> **状态说明**：本轮改动完成了"把 DMA 缓冲计入播放头"的代码路径与自报量
> （`device_latency_ms`），并给出下面的实测流程；**物理测量必须在实机上做一次**，
> 因为它依赖具体声卡/驱动的缓冲行为。软件侧无法替代。

按成本从低到高，三种手段：

### 3.1 手段 A：只信驱动自报（零成本，默认）

WASAPI 的 `IAudioClock` 是驱动自己的采样计数，`playback − callback` 就是驱动对
"这批数据什么时候出声"的承诺，精度通常在 1 ms 量级。所有做 A/V 同步的播放器
用的都是这个量。**日常使用就用它，不需要额外动作。**

验收：日志里 `声卡 N ms` 落在 10–30 ms。若恒为 0，说明该后端没给时间戳，
代码会退回 0（即播放头按"填缓冲位置"算，误差 = 一个缓冲长度）。

### 3.2 手段 B：环回线（推荐，±2 ms）

一条 3.5 mm 线把播放设备的输出接回**另一块**声卡的输入（同一块声卡也行，
只要驱动支持"线路输入 + 输出"同时工作）。

1. 播放设备选**真实声卡**（不能用 VB-Cable，虚拟设备没有 DAC 延迟）。
2. 手机端开 1 kHz 测试音，PC 端正常接收，等日志出现稳态水位。
3. 用录音软件同时录环回输入 10 s（48 kHz WAV）。
4. 在录音里量出"1 kHz 的起始沿"相对录音文件起点的位置——由于录音起点与日志
   不同源，这一步只能测**变化量**：
   - 记下稳态 `total_latency = L1`，以及录音里的相位基准 `P1`；
   - 临时**抬高或降低**目标水位 60 ms 左右，记录 `total_latency = L2` 与 `P2`；
     Windows 侧不必重编译：`set UDP2CAL_WATER_TARGET_MS=210` 重启即生效（允许区间
     80–600 ms，越界钳位），测完清掉变量回到默认 150。本步只涉及 PC 作为接收端的
     目标，不受 Android 侧常量影响；但长期改值必须同步两端（`WATER_TARGET_MS` 必须同值）。
   - 检查 `(P2 − P1)` 是否 ≈ `(L2 − L1)`。相等即证明播放头换算与
     `device_latency` 的符号、量级都正确。
5. 若二者差一个常数 `C`，把 `C` 记为**该机器的展示修正量**：

```
displayed_latency = total_latency + C
```

注意 `C` 里同时含 DAC 与 ADC 的延迟（环回线把两者都算进去了）。
它对**听感延迟**没有意义，只用于把界面上的数字调准。

### 3.3 手段 C：声学（音箱 + 麦克风，±5 ms 以上）

只有在没有环回线时才用。空气传播约 2.9 ms/m，麦克风自身还有几毫秒，
精度天然不如手段 B：

1. 麦克风距音箱 1–2 cm，录音 48 kHz。
2. 关闭系统音效增强（空间音效/响度均衡会引入几十毫秒且不可测）。
3. 按 3.2 的"变化量"法比对，不要试图比对绝对值。

### 3.4 判定表

| 观测量 | 期望 | 不满足时 |
| --- | --- | --- |
| `device_latency_ms` | 10–30 ms（10 ms 缓冲 + 一个混音周期） | 恒 0 → 后端无时间戳，按 20 ms 兜底即可 |
| 水位变化 Δ 与录音延迟变化 Δ 一致 | \|差\| ≤ 5 ms | 检查是否把 `played_frames` 与 `pipe_ms` 混用（差一个 `device_latency`） |
| 稳态 `total_latency` | v1.4.0 验收 ≤190 ms（水位 150 上下波动） | 明显超出先看水位，再看声卡缓冲 |
| 反馈量（10 s 内） | \|Δu\| 收敛到 100ppm 以内 | 一直顶满说明前馈没工作，检查 `σ`/桶数 |

## 4. 不要做的事

- **不要**用"墙钟 − 播放头对应媒体时间"直接当作端到端延迟：那是接收端本地时间线
  自洽性检查，不是物理延迟。
- **不要**为了压低延迟把 `JITTER_START_MS` 调到 20 ms 以下：Wi-Fi 的调度抖动
  经常超过 10 ms，会把延迟换成 PLC 破音。
- **不要**用离散丢/插去追水位：那是 2026-10 之前的老做法，代码里已整条删除
  （`SLIP_*`、`slip_drop`/`slip_insert`、Kotlin `PcmSlip`），现在只有重采样比率
  一个执行手段（见 `PROTOCOL_V3_RTP.md` 7.9）。
- **不要**为了"更快收敛"把 `PI_TI_S` 调小：水位是速率差的纯积分，PI 叠上去就是
  双积分器（ζ = √(K_plant·KP·Ti)/2）。`Ti=10 s` 曾让 ζ≈0.35，网络每次抖动都把环
  敲响，听感是"几十秒一次循环的变调"；现在是 `Ti=90 s`（ζ≈0.67）。
- **不要**放大 `PI_KP_PER_MS`：它同时决定"水位回多快"和"变调多响"
  （`d水位/dt = −1000·adjust`），20 ms 偏差 = 400 ppm ≈ 0.7 音分就是上限。

## 5. 高频诊断（P0 基线，实机微调用）

设环境变量 `UDP2CAL_ASRC_DIAG=<采样周期 ms>`（例如 `20`）启动 Windows 端，
会在 `%LOCALAPPDATA%\UDP2CAL\asrc_diag.csv` 覆盖写出一份最多 300 s 的原始序列：

```
t_s,ring_ms,pipe_ms,jb_ms,water_ms,target_ms,adjust_ppm,ff_ppm,sigma_ppm,buckets,played_s,highest_ts,next_ts,plc,underrun,trims
```

用途（不需要外部设备）：

- `water_ms` 的均值/标准差 → 判断稳态是否真钉在目标、抖动有多大；
- `adjust_ppm` / `ff_ppm` → 看反馈是否收敛到 0、前馈是否稳定（钟差应是小常数）；
- `sigma_ppm` 与 `buckets` → 判断前馈有没有可用的观测窗；
- `plc` 增长 → 供水不足（水位太低或网络抖动超出缓冲）；
- `trims` 增长 → 阶跃吸收在干活（一次补齐被整帧跳掉，不计入 `plc`）；稳态下应接近不增长，
  持续增长说明目标对该环境偏低或判据过激（见 `PROTOCOL_V3_RTP.md` §7.10.2）。

### 5.1 已知环境基线

**v1.3.0（2026-10-26，未关手机扫描，Android + Wi-Fi + VB-Cable 48 kHz）**

| 观测 | 值 | 含义 |
|------|-----|------|
| 长期到达率 | 99.99 帧/s | 发送端节拍正常 |
| 单次到位突发 | 中位 9 帧 = **90 ms**，约每 1.2 s 一次 | 包被 AP/Wi-Fi 成批交付 |
| 周期性断供 | 每隔几十秒一次 **~200 ms** | 断供期只能依靠 PLC，随后十几帧一起到 |
| `ff_ppm` | 中位 4，`σ` 中位 13 | 两端晶振差可忽略 |
| `ring_ms` | 40–49（中位 44） | 解码节流在 `DECODE_LIMIT_MS` 上下正常振荡 |
| `jb_ms` | 中位 220（170–270，尖峰可达 440） | 本环境必须的抖动缓冲，由断供幅度决定 |

当时结论：`WATER_TARGET_MS` 必须 ≥ 解码环 + 声卡 + **断供幅度**，故定为 **260 ms**
（总延迟约 275–285 ms）。把目标压到 70 ms 会让 PI 永久顶满 `RESAMPLE_MAX_ADJUST`
（实测 +3684 ppm，即常年 ~6 音分变调）、水位在 120–306 ms 之间慢锯、PLC 升到 3–8 次/分；
260 ms 下水位中位 275–284 ms、PLC 0.4–1.1 次/分、反馈量中位接近 0，且不再长期贴钳位。

**v1.4.0（关扫描 + DSCP EF + 阶跃吸收）**：上表那 200 ms 级的断供来自手机全频段扫描
（`com.vivo.multinlp`，每 60–120 s 占用无线 1.85 s）。`adb shell pm disable-user --user 0
com.vivo.multinlp` 之后 4 次长跑 **0 次 >200 ms**，稳态空档只剩 68–90 ms，因此目标降到
**150 ms**（环 44 + 声卡 ~10 + 抖动余量 ~96 —— 安全系数 1.6 × 68–90 ≈ 140 → 取 150）。
v1.4.0 验收口径：`water_ms` 中位 150±20 ms、标准差 <25 ms、`adjust_ppm` 顶满占比 <5%、
PLC <2 次/分、端到端总延迟 ≤190 ms。偶发的一次补齐不再靠水位全量预留，而由阶跃吸收
（`trims` 列）当场吃掉。

换环境后仍要重跑本节的开环采样（`UDP2CAL_ASRC_DIAG=20`），目标取「实测最大空档 ×1.5–1.6」。
Windows 侧可直接用 `UDP2CAL_WATER_TARGET_MS`（允许 80–600 ms，越界钳位，首次读取后缓存）
现场试，定值后回写常量并同步 Android（`WATER_TARGET_MS` **两端必须同值**）。
**不要靠压低目标去赢延迟。**

判读捷径：若 `adjust_ppm` 长时间贴在 ±5000，说明目标不可达（或者真有超过 ±0.5% 的钟差）；
`ff_ppm` 大跳后自行归零属正常（时间线重建，`RATE_JUMP_MAX_SAMPLES` 会作废旧窗口）。
