# 总延迟实测校准

> 适用：协议 v3（RTP/Opus，固定 10 ms 帧）。
> 目标：把“接收端可听点延迟”的绝对值钉准一次，并给出一套能区分**设备钟差**、
> **网络攒批**、**丢包/断流**、**设备缓冲深度**的验收方法。

---

## 1. 三个量的关系

| 量 | 含义 | 获取方式 |
| --- | --- | --- |
| `water_ms` | 抖动缓冲 + 解码环 + 声卡缓冲（控制口径） | `jb.water_ms() + ring_ms + device_latency_ms` |
| `device_latency_ms` | 数据填进声卡缓冲到真正发声的时间 | cpal `timestamp().playback − .callback`（WASAPI `IAudioClock::GetPosition` + QPC） |
| `total_latency` | 正在播放的那一帧“到达本机”到“出声”的时长 | `now − arrival(audible_ts)` |

**`played_frames` 不含 DMA 缓冲**：cpal 输出回调每填一次缓冲就把 `played_frames`
前移，这段数据还要经过 WASAPI 引擎缓冲 + DMA 才出声。因此可听点换算要减掉
`ring_frames + device_latency_frames`：

```text
queued_media = (ring_frames + device_latency_frames) × current_ratio()
audible_ts   = jb.next_ts() − queued_media
```

`audible_ts` 已经含了声卡缓冲，所以：

```text
total_latency = now − arrival(audible_ts)          # 不要再 + device_latency_ms
```

再加一次 `device_latency_ms` 会把同一段声卡等待计算两遍，数字会偏大一个缓冲区。
`total_latency` **不含**发送端采集→发包与单程网络时延——没有跨设备时钟就测不出来。
发送端必须在采集/读取/编码/发送各段分别打点（见 `PROTOCOL_V3_RTP.md` §8.1）。

Android 没有独立的 PCM 环：`ring_ms` 取 `written − playbackHead`，`device_latency_ms`
按 0 处理，避免重复计算；播放头读数失败时宁可打日志并保持旧值，也不要伪造 0。

## 2. 打印基线（不需要任何外部设备）

启动后每 10 s 会有一行日志：

```
[Latency] 总延迟≈170ms（水位 150ms = 抖动 96 + 解码 44，目标 150）声卡 10ms 比率 +0.005%（反馈 -46ppm / 设备前馈 +4ppm，σ 13.0ppm，24 桶，阶跃裁剪 0 帧）
```

（示例数值，实际以本机日志为准。）

判读：

| 现象 | 结论 |
| --- | --- |
| 水位在 130–170 ms 之间小幅波动，标准差 <25 ms | 正常。慢 PI 把长期均值钉在目标上 |
| `adjust_ppm` 长期贴 ±5000 | 目标不可达，或真有超过 ±0.5% 的钟差；先查水位再查设备采样率 |
| 设备前馈长期贴 ±20000ppm | 不是钟差（钟差不会这么大），检查时间线是否被重建 |
| `σ` 长期很大（>200ppm）或桶数不涨 | 设备进度观测不足；前馈未发布，只剩慢 PI |
| 反馈量长期顶满而前馈≈0 | 前馈窗口没攒够，或水位被外部因素持续推走 |
| `声卡 0ms` | 该后端未提供 `playback` 时间戳；换 WASAPI 共享/独占后再看 |
| `trims` 稳态持续增长 | 目标对该环境偏低或存在持续积压，先重定目标（§5.1） |

## 3. 实测校准

> **状态说明**：软件侧已把设备进度（Windows `IAudioClock`/QPC、Android 播放头）
> 接入前馈与可听点换算；物理绝对值仍依赖具体声卡/驱动，**必须在实机上做一次**。

按成本从低到高，三种手段：

### 3.1 手段 A：只信驱动自报（零成本，默认）

WASAPI 的 `IAudioClock` 是驱动自己的采样计数，`playback − callback` 就是驱动对
“这批数据什么时候出声”的承诺，精度通常在 1 ms 量级。日常使用就用它。

验收：日志里 `声卡 N ms` 落在 10–30 ms。若恒为 0，说明该后端没给时间戳，
代码会退回 0（误差 = 一个缓冲长度），此时应换后端或接受该误差。

### 3.2 手段 B：环回线（推荐，±2 ms）

一条 3.5 mm 线把播放设备的输出接回**另一块**声卡的输入（同一块声卡也行，
只要驱动支持“线路输入 + 输出”同时工作）。

1. 播放设备选**真实声卡**（不能用 VB-Cable，虚拟设备没有 DAC 延迟）。
2. 手机端播放测试信号（**PRBS / 扫频 / 脉冲串**，不要只用 1 kHz 正弦：
   1 kHz 相位每 1 ms 重复一次，无法唯一确定几十 ms 的延迟）。
3. PC 端正常接收，等日志出现稳态水位。
4. 用录音软件同时录环回输入 10 s（48 kHz WAV），并让录音文件与 PC 日志共用
   同一个起始参考（例如录音开始时打一条日志标记）。
5. 先记稳态 `total_latency = L1` 与录音互相关峰位置 `P1`；临时把目标水位
   抬高/降低约 60 ms，记录 `L2`、`P2`：
   - Windows 侧不必重编译：`set UDP2CAL_WATER_TARGET_MS=210` 重启即生效
     （允许 80–600 ms，越界钳位），测完清掉变量回到 150；
   - 该变量只影响 **Windows 作为接收端**的这一个方向，不要求 Android 同值；
   - Android 反向接收的目标由 Android 常量独立决定，改 Windows 不会影响它。
6. 检查 `(P2 − P1)` 是否 ≈ `(L2 − L1)`。相等即证明可听点换算与
   `device_latency` 的符号、量级都正确。
7. 若二者差一个常数 `C`，把 `C` 记为**该机器的展示修正量**：
   `displayed_latency = total_latency + C`。`C` 同时含 DAC 与 ADC 延迟，只用于
   把界面数字调准，对听感延迟没有意义。

### 3.3 手段 C：声学（音箱 + 麦克风，±5 ms 以上）

没有环回线时才用。空气传播约 2.9 ms/m，麦克风自身还有几毫秒，精度天然不如手段 B：

1. 麦克风距音箱 1–2 cm，录音 48 kHz。
2. 关闭系统音效增强（空间音效/响度均衡会引入几十毫秒且不可测）。
3. 按 3.2 的“变化量”法比对，不要试图比对绝对值。

### 3.4 判定表

| 观测量 | 期望 | 不满足时 |
| --- | --- | --- |
| `device_latency_ms` | 10–30 ms（10 ms 缓冲 + 一个混音周期） | 恒 0 → 后端无时间戳，记录并接受该误差 |
| 水位变化 Δ 与录音延迟变化 Δ 一致 | \|差\| ≤ 5 ms | 检查是否把 `played_frames` 与 `water_ms` 混用，或重复加了 `device_latency` |
| 稳态 `total_latency` | 接收端目标 150 ms 上下；端到端另加发送/网络 | 明显超出先看水位，再看声卡缓冲 |
| 反馈量（10 s 内） | \|Δu\| 收敛到 100 ppm 以内 | 一直顶满说明前馈没工作或目标不可达，检查 `σ`/桶数 |

**验收不再只卡“≤190 ms”一个数**：150 ms 是接收端水位目标，端到端还包含采集、
编码、发送排队与网络；设备/环境不同不能用一个固定毫秒数一刀切。必须同时记录
水位、比率、PLC、trims、underrun 与录音对齐结果。

## 4. 不要做的事

- **不要**用“墙钟 − 播放头对应媒体时间”直接当作端到端延迟：那是接收端本地时间线
  自洽性检查，不是物理延迟。
- **不要**为了压低延迟把 `JITTER_START_MS` 调到 20 ms 以下：Wi-Fi 的调度抖动
  经常超过 10 ms，会把延迟换成 PLC 破音。它是硬下限，不是启动目标。
- **不要**用离散丢/插去追水位：代码里已整条删除（`SLIP_*`、`slip_drop`/`slip_insert`、
  Kotlin `PcmSlip`），现在只有重采样比率一个连续手段（见 `PROTOCOL_V3_RTP.md` §7.9）。
- **不要**为了“更快收敛”把 `PI_TI_S` 调小：水位是速率差的纯积分，PI 叠上去就是
  双积分器。`Ti=10 s` 曾让 ζ≈0.35，网络每次抖动都把环敲响，听感是“几十秒一次
  循环的变调”；现在 `Ti=180 s`，且水位先过 4 s 低通，网络攒批不再进入音高。
- **不要**放大 `PI_KP_PER_MS`：它同时决定“水位回多快”和“变调多响”
  （`d水位/dt = −1000·adjust`），20 ms 偏差 = 400 ppm ≈ 0.7 音分就是上限。
- **不要**把设备缓冲加进 PLC 判据：`ring_ms <= PLC_LEAD_MS` 只看 PCM 提交余量；
  设备缓冲再深也不能证明还有数据可提交。

## 5. 高频诊断（P0 基线，实机微调用）

设环境变量 `UDP2CAL_ASRC_DIAG=<采样周期 ms>`（例如 `20`）启动 Windows 端，
会在 `%LOCALAPPDATA%\UDP2CAL\asrc_diag.csv` 覆盖写出一份最多 300 s 的原始序列：

```
t_s,ring_ms,pipe_ms,jb_ms,occupancy_ms,water_ms,target_ms,adjust_ppm,ff_ppm,sigma_ppm,buckets,played_s,highest_ts,next_ts,plc,underrun,trims
```

用途（不需要外部设备）：

- `water_ms` 的均值/标准差 → 判断稳态是否真钉在目标、抖动有多大；
- `occupancy_ms` 与 `jb_ms` 的差 → 媒体空洞 vs 真实占槽；阶跃吸收只看前者；
- `adjust_ppm` / `ff_ppm` → 看反馈是否收敛、设备前馈是否稳定（钟差应是小常数）；
- `sigma_ppm` 与 `buckets` → 判断设备进度观测窗是否可用；
- `[Pacer] 30s` 日志行（`min/avg/max`，单位 µs）→ 反向发送节拍的迟到量：
  末尾的 `重锚=n` 是"迟到超过半个帧、槽位被迫重锚"的次数：它不计入 `min/avg/max`
  （那三列只描述网格**没被撕开**时的精度）。空闲期无声、线程被抢占、设备重开
  都会让 `重锚` 增长，所以判读顺序是：先看 `重锚` 是否与 `帧` 同数量级（是 →
  发送根本不连续，不是抖动问题），再看 `min/avg/max`。
  稳态 `max` 应在几百 µs 量级；若 `max` 周期性跳到 5–16 ms，说明高精度定时器
  不可用（启动日志会有 `[Reverse] 高精度定时器不可用`），10 ms 网格正在被系统
  tick 量化；`max` 偶发上百毫秒则是线程被抢占（磁盘/杀软/电源策略），需要对照
  同时段的其他日志。
- `[RTP]` 行里的 `FEC=n`（每窗口清零）→ 本窗口内有多少帧是**用下一个包的
  LBRR 重建**出来的（§8.7）。它与 `PLC` 是此消彼长的关系：`FEC` 涨而 `PLC` 不涨
  表示有丢帧但都补回来了（听不出来）；两者一起涨、且 `PLC` 明显偏大，说明发送端
  没开 in-band FEC（手机端 `Opus 带内 FEC` 开关）或下一个包也一起丢了。
- `plc` 增长 → 供水不足（目标太低或网络抖动超出缓冲）；
- `trims` 增长 → 阶跃吸收在消费帧（逐帧解码后丢弃 PCM，不计入 `plc`）；
  稳态应接近不增长，持续增长说明目标偏低或判据过激（§7.10.2）。

### 5.1 验收矩阵（必须逐项做，不能只看“没断音”）

| # | 注入条件 | 期望 |
|---|---------|------|
| 1 | 网络无抖动，仅设备时钟误差（例如播放设备 ±200/±300 ppm） | 前馈收敛，`adjust_ppm` 稳定在相应值；音高稳定；无 trims |
| 2 | 网络只有攒批（90 ms 一次补齐），设备时钟正常 | 水位锯齿可见，但 `adjust_ppm` 不被单次到达推走；`trims` 不因单次增长触发；无周期性变调 |
| 3 | 单包丢失 | 1 帧 PLC，恢复后无接缝爆音；解码器状态连续 |
| 4 | 200 ms–2 s 断流 | PLC 最多 12 帧后静音；恢复包按时间戳接纳；不永久静音；必要时应显式 resync |
| 5 | 设备缓冲 10/20/30/50 ms | 缺包时都在欠载前补 PLC；`underrun` 不因设备缓冲变深而增加 |
| 6 | 阶跃积压持续 >1.5 s | 逐帧解码后丢弃 PCM，`trims` 增长、`plc` 不增长；接缝无爆音 |

测试信号用 **PRBS / 扫频 / 脉冲串**，录音与日志共用起始参考。每次记录：
最终 `adjust_ppm`（ASRC 比率）、`trims` 实际消费帧数、`underrun`、`plc`、resync 次数，
并与输出录音对齐。

### 5.2 已知环境基线

**v1.3.0（2026-10-26，未关手机扫描，Android + Wi-Fi + VB-Cable 48 kHz）**

| 观测 | 值 | 含义 |
|------|-----|------|
| 长期到达率 | 99.99 帧/s | 发送端节拍正常 |
| 单次到位突发 | 中位 9 帧 = **90 ms**，约每 1.2 s 一次 | 包被 AP/Wi-Fi 成批交付 |
| 周期性断供 | 每隔几十秒一次 **~200 ms** | 断供期只能依靠 PLC，随后十几帧一起到 |
| `ff_ppm` | 中位 4，`σ` 中位 13 | 两端晶振差可忽略 |
| `ring_ms` | 40–49（中位 44） | 解码节流在 `DECODE_LIMIT_MS` 上下正常振荡 |
| `jb_ms` | 中位 220（170–270，尖峰可达 440） | 本环境必须的抖动缓冲，由断供幅度决定 |

当时结论：`WATER_TARGET_MS` 必须 ≥ 解码环 + 声卡 + **断供幅度**，故定为 **260 ms**
（总延迟约 275–285 ms）。把目标压到 70 ms 会让 PI 永久顶满 `RESAMPLE_MAX_ADJUST`
（实测 +3684 ppm，即常年 ~6 音分变调）、水位在 120–306 ms 之间慢锯、PLC 升到 3–8 次/分；
260 ms 下水位中位 275–284 ms、PLC 0.4–1.1 次/分、反馈量中位接近 0。

**v1.4.0（关扫描 + DSCP EF + 阶跃吸收）**：上表那 200 ms 级断供来自手机全频段扫描
（`com.vivo.multinlp`，每 60–120 s 占用无线 1.85 s）。`adb shell pm disable-user --user 0
com.vivo.multinlp` 之后 4 次长跑 **0 次 >200 ms**，稳态空档只剩 68–90 ms，因此目标降到
**150 ms**（环 44 + 声卡 ~10 + 抖动余量 ~96 —— 安全系数 1.6 × 68–90 ≈ 140 → 取 150）。
v1.4.0 验收口径：`water_ms` 中位 150±20 ms、标准差 <25 ms、`adjust_ppm` 顶满占比 <5%、
PLC <2 次/分。偶发的一次补齐不再靠水位全量预留，而由阶跃吸收（`trims` 列）当场吃掉。

**v1.5.1（2026-10-28，同一条链路，双目标实测）**

| 目标 | 总延迟 | 分解（抖动 + 解码 + 声卡） | `PLC` / `迟到` | `[Pacer]` min/avg/max | 反馈 / 前馈 |
|------|--------|--------------------------|----------------|----------------------|-------------|
| 150 ms | 156–168 ms | 100–120 + 52–56 + 10 | 0 / 0 | 21/300/1000 µs | +29…+61 ppm / −20…+99 ppm |
| 80 ms | 83–99 ms | 30–50 + 44–59 + 10 | 0 / 0 | 17/300/2880 µs | −46…−112 ppm / ±22 ppm |

由此定下的口径：**总延迟 ≈ 目标水位 + 10~20 ms**。原因是目标只压在抖动缓冲那一段，而解码环
（`DECODE_LIMIT_MS=40`，按 10 ms 成块 → 实测 44–59 ms）是结构性的；要让总延迟低于 80 ms，
动目标没有用，必须改 `DECODE_LIMIT_MS`（同时受 `PLC_LEAD_MS 20 + DECODE_LIMIT_MS 40` 的下界约束）。

同一链路在目标 150 的那一轮还出现过一次 >100 ms 到达停顿（`迟到=3 PLC=3`）：目标 80 时同样的停顿
会变成 7–10 帧 PLC。**这就是默认值仍留 150 的理由**——80 只在实测空档 <40 ms 的链路上合适。

换环境后仍要重跑本节的开环采样（`UDP2CAL_ASRC_DIAG=20`），目标取「实测最大空档 ×1.5–1.6」。
Windows 正向接收可直接用 `UDP2CAL_WATER_TARGET_MS`（允许 80–600 ms，越界钳位，首次读取后
缓存）现场试；Android 反向接收改 Android 常量。**每个方向独立定值，不要求两端同值。**
**不要靠压低目标去赢延迟。**

判读捷径：若 `adjust_ppm` 长时间贴在 ±5000，说明目标不可达（或者真有超过 ±0.5% 的钟差）；
`ff_ppm` 大跳后自行归零属正常（时间线重建，`RATE_JUMP_MAX_SAMPLES` 会作废旧窗口）。
