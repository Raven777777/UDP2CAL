**UDP + RTP + Opus 这条技术路线可以继续，但接收端的时钟与播放控制需要重新梳理。现在的设计能维持连续输出，却会主动引入变调和时间跳跃；这与你目前的听感相符。**

**1．整体架构有可保留的骨架**

这些选择本身合理：

| 现有选择 | 评价 |
|---|---|
| 局域网 UDP、固定 48 kHz / 10 ms、Opus | 适合当前双向音频用途 |
| 网络线程只收包，独立线程解码 | 有助于隔离网络与音频调度 |
| Windows 回调只搬运 PCM，无锁、无分配 | 应继续坚持 |
| 有界抖动缓冲与 PCM 环 | 能限制积压，便于分析延迟 |
| 两端共享 Rust 协议算法 | 能减少算法实现分歧 |
| 声卡消费驱动输出 | 方向正确 |

真正需要修改的是这些组件之间的控制关系。当前设计把**采样时钟差、网络到达抖动、缓冲目标变化、异常恢复**都压到了水位控制与时间线跳跃上，几个机制会相互激发。

**2．音调漂移是当前控制方式能够直接产生的结果**

协议 §7.9 用同一个重采样比率处理两件事：补偿设备时钟差，以及把水位拉回固定目标。

其中第二件事会改变播放速度，也会改变音调。以文档的比率定义计算，持续使用 `+0.5%` 会升高约 **8.6 音分**。把参数调柔和能减轻这种变化，但无法消除这条因果关系。

文档里的网络基线尤其值得注意：音频经常以约 90 ms 一批交付。批次到达前，水位下降；到达后，水位回升。**这种往复变化本身不代表长期采样速率失配。** 如果控制器持续追踪它，网络交付节奏就可能被转成播放速度变化。

当前水位低通的时间常数约 150 ms，仍会响应这类波动。文档中“调整 PI 后，音调波动从 13.5 音分降到 3 音分”的结果，证明了改善，也说明控制器仍在把网络扰动传给音调。

建议重新划清职责：

| 要解决的问题 | 合适的主要机制 |
|---|---|
| 长期采样速率不同 | 缓慢、连续的 ASRC 校正 |
| 包成批到达、乱序 | 抖动缓冲与到达统计 |
| 需要改变播放延迟 | 独立的延迟调整策略 |
| 丢失或来不及的音频 | PLC，以及恢复时的衔接 |
| 真实时间线断裂 | 明确的重同步 |

水位反馈仍可保留，用于修正长期残差；它需要避免追逐每次网络起伏。需要回收较大的延迟时，可以评估保音调的时间伸缩。WebRTC NetEq 就把延迟目标、加速/减速、PLC、恢复衔接分别处理。保音调伸缩也有音质代价，需要测量，不能当作无损操作。[webrtc.googlesource.com](https://webrtc.googlesource.com/src/%2B/refs/heads/main/modules/audio_coding/neteq/g3doc/index.md?utm_source=chatgpt.com)

**3．“轻微突变”首先应检查阶跃裁剪**

协议 §7.10.2 明确规定：满足条件后，直接跳过 **10–120 ms** 音频，每分钟允许三次。

这意味着当前系统本身允许发生可听的时间跳跃。“每分钟三次”只是频率限制，不能作为音质保证。

这里还有两个更具体的问题。

其一，**单次水位增长超过 80 ms，不能充分证明积压增加了。** 假设网络暂停交付 90 ms，随后补齐九帧；如果播放缓冲覆盖了这段空档，补齐只是恢复正常水位。应判断补齐后是否形成持续的额外延迟，并结合此前消耗与 PLC 情况，不能仅凭增长速度决定删除内容。

其二，文档规定 `skip_frames()` 跳过编码包，同时保持解码器状态，不产生 PLC。Opus 是有状态、存在跨块重叠的编解码器；官方要求按顺序处理包，缺失部分可以通过 PLC 推进。直接跨过一段，再把后续包送入旧状态，存在恢复失真的风险。**这一点需要查源码确认。**[opus-codec.org](https://opus-codec.org/docs/opus_api-1.5/group__opus__decoder.html?utm_source=chatgpt.com)

如果确实需要舍弃一段已有音频，可以评估顺序解码后在 PCM 层进行裁剪和衔接；严重断裂则走重同步。两者都需要明确处理接缝。

**4．时钟模型还没有完全统一**

文档说“声卡是唯一时钟”，但前馈估计器使用的是：

`RTP 时间戳 ↔ Instant / System.nanoTime 到达时刻`

它估计到的是**发送端媒体时钟相对于接收端系统单调时钟的速率**。输出重采样实际需要匹配的是**发送端媒体时钟相对于接收端音频设备时钟的速率**。

系统时钟与音频设备时钟不能默认完全一致。因此，“频差全部由前馈承担，反馈工作点永远接近零”这个保证不成立。反馈长期承担一部分设备钟差，可以是正常现象。

应明确三种时间参照：媒体采样时间、接收端单调时间、接收端音频设备进度，并建立可验证的映射。Windows 的 `IAudioClock::GetPosition` 能提供设备位置及其对应的 QPC 时间，正是这种映射所需的信息。[Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition?utm_source=chatgpt.com)

另外，协议给前馈 ±2%、反馈 ±0.5%，然后相乘。如果最终没有再限幅，最高可以达到 **+2.51%**。所以“系统只有 ±0.5% 微调权限”的描述需要查实现确认。

**5．PLC 判据存在一个需要优先核查的边界风险**

当前伪代码是：

`pipe_ms = ring_ms + device_latency_ms`

只有 `pipe_ms <= 20` 才补 PLC。

按这段规则，如果设备报告延迟 30 ms，即使 PCM 环已经为空，判据仍然不成立。回调可能已经开始填静音，解码线程却继续等待缺失包。

这里混淆了两个时刻：

- 音频最终呈现给用户的时刻；
- 下一段 PCM 必须提交给输出接口的截止时刻。

设备里已经排着的声音，不能保证应用还有时间提交下一段。Windows 的 endpoint padding 表达的是设备缓冲内尚未消费的数据量；它与固定或预测的设备延迟应分别理解。[Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getcurrentpadding?utm_source=chatgpt.com)

**如果源码确实照这段伪代码实现，这是高优先级问题。** 应模拟设备延迟 10、20、30、50 ms，检查缺包时是否都能及时生成 PLC，以及是否先发生输出欠载。

Android 也要核实已写入帧数、播放进度和实际排队量。阻塞式 `AudioTrack.write()` 提供背压，但返回不代表声音已经播放；官方也明确提示，写入不及时会产生欠载和爆音。[developer.android.com](https://developer.android.com/reference/android/media/AudioTrack?utm_source=chatgpt.com)

**6．有几条文档结论需要纠正，它们会影响架构判断**

| 当前表述或规则 | 审查结论 |
|---|---|
| 双向 `WATER_TARGET_MS` 必须相同 | 两个方向分别接收、分别播放，通常可以有独立目标。除非另有未写出的耦合机制，否则无需强制相同 |
| DTX 未发送的帧也递增 RTP 序列号 | 偏离标准 RTP。序列号按发送包递增，时间戳保留采样时间；接收端不应在每次 PLC 时虚构一个已发送包序号 |
| 30 ms 预缓冲启动，随后追到 150 ms | 需要明确启动策略。若仅靠最大 0.5% 的减速积累额外 120 ms，理论上至少需要约 24 秒 |
| `highest_ts − next_ts` 是“已收到的音频量” | 它表达媒体跨度，里面可能含缺包或静音空洞；应与实际包占用量、连续可解码量分别统计 |
| 启用 DRED 后就具备冗余恢复能力 | 需要确认接收端确实解析并使用 DRED；文档播放算法目前只展示普通解码和 PLC |
| 每次 `OPUS_SET_*` 都重置编码器 | 不能这样概括。避免无意义重配合理，但应核查具体 CTL 或封装行为 |

其中 RTP 序列号问题有明确标准依据：DTX 的采样时间继续前进，并不要求为未发送的静音帧递增序列号。当前文档为修复接收端恢复问题而改变发送端语义，会影响标准工具的丢包统计与互操作。[rfc-editor.org](https://www.rfc-editor.org/rfc/rfc3550.html?utm_source=chatgpt.com) DRED 则有专门的解析与恢复接口，编译启用、发送冗余和使用冗余需要分别验证。[opus-codec.org](https://opus-codec.org/docs/opus_api-1.5/group__opus__decoder.html?utm_source=chatgpt.com)

**7．发送端需要检查“隐形积压”**

目前发送线程同时执行采集、编码、节拍等待和发送。“没有应用层 PCM 队列”是一个实现特点，但不等于没有积压。

如果采集接口一次交付多帧，而线程为了按 10 ms 网格发包停止读取，剩余数据可能继续积在 AudioRecord 或 WASAPI 缓冲中。此时延迟已经在发送端增长，接收端看到的却可能仍是整齐的包间隔。

因此需要测量：**每段音频的采集时间、读取时间、编码完成时间和发送时间**。发送整形器还应说明落后时究竟舍弃哪段音频，以及时间戳如何保留这段真实缺口。

缓冲是否有界、是否知道里面的数据有多旧，比“完全没有队列”更能说明实时性。

**8．当前测量与验收还不足以证明听感稳定**

LATENCY_CALIBRATION(1).md[延迟校准文档](sandbox:/workspace/scratch/603ba594ba02/upload/LATENCY_CALIBRATION(1).md)已经承认，界面数值不包含发送端和网络延迟。但根 README 仍写端到端 50–80 ms，验收又写 ≤190 ms，与当前 150 ms 总水位目标并未使用同一口径。

另外，如果 `audible_ts` 已经对应“此刻正在播放的音频”，那么 `now − arrival(audible_ts)` 已包含此前设备内等待；再加一次设备延迟，存在重复计算风险。应查实际取样时刻和变量语义。

校准中的连续 1 kHz 正弦也有局限：相位每 1 ms 重复，无法单凭相位唯一确定几十毫秒延迟。实际校准宜使用有共同录制参考的脉冲、扫频或伪随机序列。

验收还需要覆盖音频结果本身。目前“PLC 少、没有断流、水位接近目标”不能证明没有变调和跳音。最有价值的几组验证是：

- **无网络抖动，只注入设备钟差**：检查 ASRC 是否稳定补偿。
- **无设备钟差，只注入成批交付**：检查是否产生周期变调或误裁剪。
- **单次丢包与长断供恢复**：检查 PLC、解码器状态和衔接。
- **不同设备缓冲深度**：检查提交截止时刻与欠载。

同时记录最终 ASRC 比率、裁剪的实际时长、欠载、PLC 和重同步，并与输出录音对齐。这样才能把“听到一次突变”对应到一个具体动作。

**9．技术线路的取舍建议**

当前可信局域网、单手机与单 PC 的范围，支持继续使用自研 RTP/Opus。迁移整套通信栈成本较高，现有证据更支持先整理接收控制。

建议保留现有传输和线程骨架，让每个方向独立拥有：到达统计、延迟目标、设备时钟映射、慢速 ASRC、PLC 与恢复衔接。共享 Rust 核心负责算法，平台层负责提供准确的设备进度与输出需求。

控制面已有的 ACK 校验、旧会话关联和端点绑定问题也值得处理，尤其要保证正常保活不会重建音频链路；共享 socket 本身可以保留，耗时的控制操作需要与实时收包隔离。

**目前最值得先核查的是三处：阶跃裁剪是否与突变同步发生，最终重采样比率是否与音调变化同步，以及 PLC 是否按输出提交需求及时触发。** 这三处能直接检验当前架构是否正在制造你听到的问题，再据此决定接收核心的重构范围。
