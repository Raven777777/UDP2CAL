## 一、背景

v3 的时钟模型只有一条规则：**声卡消费节奏是唯一音频时钟**（`PROTOCOL_V3_RTP.md` §7.10）。
这一条是对的。但围绕它长出的偏移修正机制，已经偏离了行业标准的 ASRC 做法：

1. **同一个缓冲被两个时域各算一遍。** 调度器要 `playhead_ts`（48 kHz 样本域），
   控制器要 `water`（毫秒域）。`note_ratio_correction`、`note_pcm_correction`、
   `offset_frac` 三路补丁存在的唯一目的，就是防止这两个量背道而驰。
   `main.rs` 解码循环里 `note_ratio_correction` 被复制进 4 个分支（Packet / Plc 解码成功 /
   Plc 静音 / Silence），这是臃肿最直观的来源。
2. **离散回落已经半废弃但仍在。** `LATENCY_CALIBRATION.md` §4 明确写着"不要用离散丢/插去追水位，
   那是 2026-10 之前的老做法"，可是代码里仍保留 8 个常量、PCM 交叉淡化几何、以及
   Rust / Kotlin 两份实现。
3. **重采样器是两点线性插值**（`audio.rs` 的 `write`）。`base_ratio == 1` 时相位恒为整数，
   是直通；但只要比率微调生效（也就是漂移校正一启动），相位就开始扫掠——见 §六 风险 1。

## 二、目标：ASRC 核心

一句话：**唯一时钟是声卡，唯一的观测量是缓冲水位，唯一的执行手段是重采样比率。**
不存在"绝对媒体时间戳 ↔ 设备帧"的双向换算，也不需要离散丢/插。

判定标准：任何需要"记住偏移"的机制，都说明中间表示选错了。

### 关键等价关系

`JitterBuffer::pull` 的缺口判定形如 `next_ts <= playhead_ts + lead`，其中
`next_ts − playhead_ts` 恰好等于"可听点之前还压着的媒体样本量"。于是它恒等于：

```
缓冲水位 ≤ lead（约 20 ms） → 补 PLC
```

同理，解码节流（`filled_frames` 上限约 40 ms）与控制器误差（`water − 目标`）也都是
**同一个量**的不同阈值。三个决策变量其实是同一个——这是 P4 能删掉整条换算链的根本原因。

## 三、技术路线

| 阶段 | 主要动作 | 验收门 | 主要风险 |
| --- | --- | --- | --- |
| **P0 诊断基线** | 临时高频打点：`water`、`highest_ts`、`played_frames` 原始序列，60 s | 拿到 σ_J 与 δ̂，确定观测窗取 10 s 还是 30 s | 无（纯观测，日志可关） |

### 依赖与门

- **P0 门 1**：σ_J 实测 → 才能定 P3 的 Ki 与观测窗。跳过 P0 直接改 PI，等于把网络抖动变成变调"呼吸"。
- **P1、P2 与主线正交**，可随时插队；P2 尤其应该尽早做（见 §六 风险 1）。
- **P3 门 2**：稳态比率残差 <20 ppm → P4 才有删除依据。
- **P4 门 3**：环回法（`LATENCY_CALIBRATION.md` §3.2）A/B 不劣化 → 才能进 P5。

## 四、关键设计：前馈管速率，反馈管相位

启动时先测量两设备钟差是**正确且值得做**的，但不要做成"标定 + 定期跳变修正"，
要做成**前馈（开环速率估计）+ 反馈（闭环水位 PI）**两条正交支路：

```
highest_ts（发送端媒体时间线）  ─┐
                                ├─→ 速率估计 dA/dD → r̂（前馈）
played_frames（设备帧计数）      ─┘

水位 L = 抖动缓冲 + PCM 环 + 声卡延迟 ──→ PI(L − 目标) → Δu（反馈）

比率 1 + u = r̂ · (1 + Δu) ──→ 相位连续重采样
```

两条支路**互不污染**：前馈的输入是计数差，与控制器的动作无关；反馈只需要处理残差。
这比"定期标定"严格更优：无限窗估计 vs 有限窗、连续 vs 跳变、能跟温度漂移 vs 会失效。

### 传感器怎么选

| 选择 | 理由 |
| --- | --- |
| 用 `highest_ts`（已扩展为 64 位）而非"已收样本数" | 丢包会让后者少计 480 样本，把估计带偏；发送端时间线不管丢不丢包都照常前进，估计无偏 |
| 回归用 `(A, D)` 计数对而非水位 | 水位是闭环量，会被自己的控制动作污染；计数差是纯开环 |
| 叠加最小延迟滤波 | 排队只会**增大**单向时延，故滑窗内 `min(now − ts/48000)` 几乎不受排队影响，可把 σ_J 再压 3–5 倍（NTP min-filter / WebRTC 自适应最小值同源）。`note_arrival` 已在记 `(ts, Instant)`，扩展即可 |
| 不新增控制面时间戳交换 | 媒体面已足够；当前控制面只有 DATA / CONNECT / DISCOVER_REQ / DISCOVER_REPLY / CONNECT_ACK |

`resync` 会重置 `highest_ts`，速率估计器必须在同一处一并重置。

### 观测窗口取多长

频率估计精度下限（σ_J 为到达抖动标准差，τ_j 为相关时间约 50 ms，T 为观测窗）：

```
σ_δ ≈ σ_J · √12 · √τ_j / T^1.5
```

| T | σ_J = 5 ms（Wi-Fi 一般） | σ_J = 2 ms | σ_J = 0.5 ms（加最小延迟滤波） |
| --- | --- | --- | --- |
| 3 s | ≈745 ppm | ≈298 ppm | ≈75 ppm |
| 10 s | ≈123 ppm | ≈49 ppm | ≈12 ppm |
| 30 s | ≈24 ppm | ≈9 ppm | ≈2 ppm |
| 60 s | ≈8 ppm | ≈3 ppm | ≈0.8 ppm |

对照典型晶振频差 100 ppm：**3 s 不够，10 s 勉强，30 s 才称得上精准。**

好消息是测量窗口几乎不花代价：不加任何校正，100 ppm 裸奔 30 s，水位只偏移 3 ms，
小于当前 5 ms 死区。因此**不需要**为标定抬高启动水位，也不需要一个"标定模式"。

### 可降级的诊断冗余

`arrival_of` 及其 128 项 `Instant` 追踪与 `water + device_latency` 是同一量的两种算法，
互为冗余。保留它作为交叉校验是合理的，但在 P4 重构播放头口径时应重新确认其必要性。

不影响稳态，但让"目标水位"这个数字失去意义。P1 统一口径。

## 六、风险与硬约束

### 风险 1：线性插值是当前最大隐患（P2 必须做）

两点线性插值在 δ=0.5 处的幅度响应为 `|cos(ω/2)|`：**12 kHz 处 −3 dB，24 kHz 处全陷**。
相位以 `u·Fs` 的速率扫过，故：

- u = 100 ppm（典型钟差）→ 扫频约 4.8 Hz，高频出现缓慢起伏
- u = 0.5%（比率顶满，即即将触发回落的工况）→ 扫频约 240 Hz，是明显的粗糙感

`base_ratio == 1` 时相位恒为整数是直通，只有比率微调生效才出现——**恰好是常年开启**。
删除第二级回落后，比率是唯一剩下的校正手段；若此时重采样器仍是两点插值，
等于把"每秒 1 ms 淡变"换成了"常年高频颤动"。这是整条路线里唯一会**变差**的地方。

ASRC 的行业标准要求是**多相 FIR（或至少三次插值）**，与比率无关。

### 风险 2：PI 与网络抖动耦合

网络抖动是**噪声**不是漂移。当前水位低通系数对应时间常数约 150 ms（带宽约 1 Hz），是合理的；
改 PI 时积分时间常数必须 **≥5 s** 且带抗饱和，否则比例项会把抖动直接变成变调。
具体取值由 P0 实测的 σ_J 决定。

### 风险 3：删除回落的边界条件

若真实钟差超过比率钳位（现为 ±0.5%），水位会单调跑偏。缓解：保留**整帧级硬重同步**
（走 jitter buffer 的 resync）兜底，而非样本级 1 ms 回落。

### 硬约束：分清"率漂移"和"阶跃"

| 类型 | 例子 | 正确工具 |
| --- | --- | --- |
| 率漂移 | 晶振频差、温度漂移 | 比率前馈（ASRC） |
| 阶跃 | 系统/其他进程改设备采样率、WASAPI 引擎周期切换、发送端节拍重置（`capture.rs` 落后 >4 帧） | jitter buffer 的 resync / PLC |

ASRC **修不了阶跃**。硬要用比率去追阶跃，只会让比率长时间顶满然后触发回落——
这正是当前第二级回落唯一的真实触发场景。P4 必须保留后一条路径。

## 八、明确不做

- **不做"定期标定 + 跳变修正"**：连续 PI 严格优于它，且代码更少。
- **不新增控制面时间戳交换**：媒体面 `highest_ts` 已足够（见 §四）。
- **不追求跨设备绝对时钟同步**：本项目无 A/V 同步需求，测出来也没有对应动作。
- **不追求更短的总延迟**：本轮目标是**把延迟钉稳**，不是把它压小。
  压低 `JITTER_START_MS` 会把延迟换成 PLC 破音，见 `LATENCY_CALIBRATION.md` §4。

## 九、验收方法

每个阶段都用同一套口径比对，方法见 `LATENCY_CALIBRATION.md` §3.2（环回线，比变化量不比绝对值）：

1. 稳态水位：10 min 内标准差与极差；
2. 稳态比率：日志里的比率微调是否稳定收敛、是否长期顶满；
3. PLC 率与欠载计数：弱网（人为丢包 / 加抖动）下不得劣化；
4. 音质：1 kHz + 扫频，12 kHz 处幅度波动（P2 专项）。

## 十一、实机微调（P0 采样结果）

环境：Windows 端 VB-Cable 输出 48 kHz（声卡缓冲 10 ms）+ Android 发送端 + Wi-Fi。
采样：`UDP2CAL_ASRC_DIAG=20`，每轮 300 s，20 ms 一行。

**观测到的三个事实**

1. 长期到达率 99.99 帧/s，而单次到位的突发中位 **9 帧（90 ms）**、约每 1.2 s 一次 →
   包被网络/AP 成批交付，**发送端节拍无锅**（Android 侧已是 10 ms 网格整形）。
2. 时钟差极小（前馈中位 4 ppm、σ 中位 13 ppm）→ 前馈支路按设计工作，但木已成舟，
   它不是水位锯齿的原因。
3. 水位锯齿的真正来源是**目标设得比网络实际断供幅度还低**：网络每隔几十秒会断供
   ~200 ms（断供期只靠 PLC 顶着，随后十几帧一起到达、`jb` 台阶式上涨），而排水能力
   ±0.5% = 5 ms/s，排掉 200 ms 要 40 s。目标设浅 → PI 永久顶满 + 水位慢锯。

**两处调参（均已落盘并双端同步）**

| 改动 | 理由 |
| --- | --- |
| `JitterBuffer::water_ms()` 改用 `highest_ts − next_ts` | 旧的"从 `next_ts` 起连续可解帧数"在乱序时瞬间塌到 0（实测 3.4 万样本中 39 次），每次都会让 PI 误以为缓冲空了而反向拉满比率 |
| `WATER_TARGET_MS` 70 → **260** | 目标必须盖住网络的**断供幅度**（~200 ms）+ 解码环 44 ms + 声卡 10 ms，而不是批次大小（90 ms）；三轮实测见下表 |
| 新增 `RATE_JUMP_MAX_SAMPLES`（2 s） | 手机重连/断流补齐会让 `highest_ts` 突跳而 `epoch` 未必变；旧窗口继续回归会出 ±2000 ppm 假前馈（实测出现） |

**效果（同一环境，300 s）**

**量测波动**：同配置重跑，水位的**中位/均值**稳定（275–284 ms），但最大尖峰在 328–490 ms

的固有代价（规范 §八：不靠变调换排水）。

网络侧动（关手机 Wi-Fi 省电 / 5 GHz / USB 网络共享），而不是调控制器。
